# Qualified expansion paths

Expansion follows proof. It is not an automatic product list.

| Adjacent outcome | Evidence trigger | Reused capabilities | New discovery |
|---|---|---|---|
| More RHEL services | Pilot meets guardrails and owner accepts maintenance | All current capabilities | New app health, recovery, and batch topology |
| Windows patching | Coordination and evidence value is demonstrated | Approval, evidence, system-of-record, health | Designated Windows patch platform and reboot semantics |
| Baseline/compliance verification | Verification evidence is trusted and reusable | Precheck, health, evidence, record update | Policy source, drift handling, remediation authority |
| Event-driven remediation | Recovery path is deterministic and low risk | Health, approval, evidence, record update | Event quality, rate limits, automatic-action boundary |
| Application release orchestration | Cross-tool handoffs are the measured constraint | Approval, quiesce, health, evidence | Pipeline ownership, deployment/rollback contracts |
| VM retirement | Evidence and ownership reconciliation are proven | Approval, precheck, evidence, record update | Data retention, dependency discovery, reclamation policy |
| Hybrid execution | Multiple sites need the same governed pattern | Most capability contracts | Network paths, execution nodes, local tools, jurisdiction |

## Qualification questions

1. Which measured result from the proof supports this expansion?
2. Is the next outcome owned and funded?
3. Which capabilities are truly reusable without weakening their contract?
4. What new human decisions, systems, and recovery paths appear?
5. Can the platform and content owners maintain the additional scope?
6. What smaller proof would reduce the new uncertainty?

## ReCommoning trigger

When a second use case needs a capability, review the local improvement for promotion to the shared catalog. Promotion requires contract tests and a maintenance owner.
